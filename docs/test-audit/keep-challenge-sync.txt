4. Same file:129 GetOrAddAsync_WeightEvictionSkipsInFlightEntries
   PROPOSE REWRITE. Useful intention: weight pressure must not detach a running shared producer. Current slow producer starts, heavy retained values create pressure, then slow is released BEFORE another request for its key. Assertions1/1/one slow call/two heavy calls verify the original waiter and post-completion retention, not whether same-key callers still share the in-flight producer during eviction.
   Plausible escaping regression: weight eviction mistakenly detaches pending key2; old waiter continues, late completion unconditionally retains its result; a concurrent caller during the gap would launch duplicate expensive work, yet this test has no such caller and can pass. Do not discard the useful resource-pressure scenario.
   Rewrite through the same public cache API: while slow remains blocked AFTER heavy pressure, register a second same-key request with a distinguishable producer; assert it cannot start another producer, then release slow and assert both receive1 and later retained lookup still1. Keep heavy eviction result separate if it becomes an unrelated reason for failure. This recommendation is about the claimed pending-generation contract, not merely the internal existence of separate pending dictionaries.

Cross-cutting result

The retained cache tests mostly earn their place: factories with generation values/call counts expose actual recomputation, eviction and retry behavior, and current map/filter consumers use these modes. Their counters are semantic production counts, not arbitrary collaborator choreography. They should not be rejected merely because caching is infrastructure. The two proposed downgrades concern a missing concurrent waiter in a purported pending-eviction test and an explicitly mixed clamp/stroke test. Claims were narrowed where assertions do not establish token-awareness or removal selectivity. No additional scaffolding or production API changes are requested by this review.
