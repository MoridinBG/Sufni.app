SYNC AND INFRASTRUCTURE TEST AUDIT — 2026-11-03

Scope and decision rule

Audited every actual test method in the 37 sources assigned to sync_infrastructure in inventory.json: 252 methods. Theory data rows count as one method. The CSV is the exhaustive ledger, with method declaration lines, specific assertions, a proposed regression and an action. Totals: KEEP 168; REWRITE 48; MERGE 22; REMOVE 14; UNPROVEN 0. Existing retention is 168/252 (66.7%); the remaining 84 do not earn retention unchanged. MERGE is not permission to discard distinct input branches: the named survivor must first absorb any behavior the ledger explicitly identifies.

This is a static audit, not an execution or mutation campaign. No production or test source changed. No tests were run because their TempDatabase/TempDirectory fixtures create files outside the project. Passing builds, green tests, test names and coverage were not used as retention evidence. Counterexamples below are reasoned from assertions and implementation, not empirical mutation results.

Required context read: AGENTS.md; docs/TESTING.md; docs/VIEW-TESTING.md; docs/ARCHITECTURE.md; docs/ARCHITECTURE-MANIFEST.md; docs/architecture/sync.md, persistence.md, ui.md, ui-workflows.md and theming.md. Production boundaries checked include the real sync/pairing coordinators, merge engine and repository implementations, protocol/AppJson declarations, HTTP owner/peer, desktop server route wiring, startup migration/connection ownership, discovery adapters and their consumers, view models, XAML and PIN control. No docs/plans were read.

A concrete implementation being internal did not automatically disqualify it. LocalDeviceIdentity/GetIdAsync, SQLite repositories/ISyncDataStore and AndroidServiceDiscovery/IServiceDiscovery implement real public contracts; observable identity persistence, row histories and native-resource lifetimes can earn KEEP. Direct helper state machines, endpoint caches, certificate predicate helpers and server mapping helpers do not earn retention merely because their methods are callable. Public serializer/migration tests can be retained for genuine compatibility behavior. Static resource inventories, object/task identity requirements, SQLite implementation counters and collaborator sequences need additional public evidence.

Highest-priority findings

1. Several tests claim stronger guarantees than their assertions measure.

   Sufni.App.Tests/SyncAndPairing/Coordinators/SyncCoordinatorClientRunTests.cs:693, SyncAll_PublishesPulledRecordedSourcesInOneBatch, only asserts two repository calls and two final store values. Publishing two separate batches would pass. REWRITE: observe StorePublication.Committed/change sets and assert one coherent notification containing both sources. The production PullIncompleteSessionSources finally block publishes the collected committed snapshots together; the test needs to observe that guarantee.

   Sufni.App.Tests/SyncAndPairing/Services/HttpApiServiceTests.cs:491, ConfirmPairingAsync_PublishesTrue_AfterCredentialsAndCertificateAreStored, observes [false,true] and reads storage only after confirmation returns. Publishing true before persistence then finishing the writes would also pass. REWRITE: gate refresh-token/incarnation/certificate writes, prove no paired notification while pending, then inspect storage at the paired notification. Current code saves tokens and certificate inside SynchronizationPeer.ConfirmPairingAsync before HttpApiService publishes.

   SyncCoordinatorClientRunTests.cs:622, SyncAll_HandlesPulledRecordedSourceOutcome, has useful valid/existing-source/repository-failure branches. Invalid hash/SST/live-JSON branches merely assert no put/no publication; a run incorrectly reporting Completed would pass.    SyncCoordinatorClientRunTests.cs:452, SyncAll_CompletesFillDownloads_BeforeAnySwapDownloadStarts, gates the HTTP fill response and checks request order. Its name and documented contract imply fill commits precede swap processing, but no committed/public state is observed. REWRITE with commit/publication gating and resulting generations.

Production architecture contradictions / code observations (not fixed)

1. Service-level stop-during-start contract gap; normal app ownership prevents the direct race. Sufni.App/Sufni.App.Desktop/SyncAndPairing/Services/SynchronizationServerService.cs:532 StartAsync stores StartCoreAsync in startTask at line541. Constructor line236 starts Initialization=Init(); Init at line345 awaits signing credentials. BuildApplication at line394 awaits Initialization. StopAsync at line546 captures only application under startGate; at line556 it returns when application is null, and neither joins/cancels startTask nor Initialization. StartCoreAsync later calls app.StartAsync at line766 and publishes application under the gate at line770. There is no linked cancellation in this service path. A direct service-level sequence can hold GetSigningKeyAsync pending, call StartAsync, await StopAsync while application is null, then release credentials successfully; start can continue building/listening/advertising after stop returned. The gate protects field access rather than completion across asynchronous work. The existing credential-failure test stops only after start already failed and does not exercise this interleaving.

   Caller ordering was checked before treating this as a product defect: Shell/Coordinators/AppStartup.cs:57 awaits backgroundTaskRunner.RunAsync(server.StartAsync, cancellation.Token); its StopAsync (line102 onward) cancels then awaits startupTask. AppShutdown.cs:64 drains startup before invoking server.StopAsync at line66. Infrastructure/BackgroundTaskRunner.cs uses Task.Run(work, token), not a cancelable WaitAsync that abandons started work. Therefore normal application shutdown drains an already-started server start before calling server stop, precluding that direct interleaving in this owner path. This is a service contract/test gap against explicit resource-drain expectations, NOT a verified reachable product race. Constructor-started Initialization before explicit StartAsync remains separately owned by the service task; no claim of runtime failure on that early path was experimentally established.

2. Legacy rear-suspension backfill is multi-statement uncheckpointed work. DatabaseMigrationRunner.cs:532 EnsureBikeRearSuspensionColumnAsync adds a destination column, updates rows, then drops legacy columns one by one outside a RunInTransactionAsync callback/versioned migration. A process interruption between dropping kind and payload columns leaves a different predecessor shape for the next launch; for example a selected missing-payload linkage draft with an orphan leverage payload can be reinterpreted after the kind column is gone. Current idempotence tests model complete launches only. This is a manifest section15 interruption/recovery risk. No migration changes or broader fixes were made.

3. The server constructor starts credential/certificate I/O before explicit StartAsync through Initialization=Init() at line236; StopAsync alone does not await it. This is part of the first service-lifetime observation, not a separate confirmed runtime defect. Construction-only graph validation does not instantiate arbitrary singleton constructors, so its KEEP does not imply this lifecycle is covered.

4. Some test names retain old ownership terminology: GetSynchronizationDataAsync_DoesNotLeakFutureRelatedTrackVersion seeds no current session-track relation; tracks are independent captured facts and session windows derive on read. The bounded future-track assertion remains useful, but the name should stop implying a stored association. Do not revive old relations just to satisfy a historical test name.

Limitations and follow-through

No tests, builds, TLS connections, live mDNS, app startup or mutation experiments were run. Public-boundary rewrites involving Apple/Socket discovery require a suitable native/browser seam; this audit does not authorize exposing internals solely for testing or creating speculative infrastructure. Production observations are narrowly derived from source and require follow-up validation before fixing. Recommended removals/merges are not implemented. Cross-owner shared support changes should be coordinated with the shell_support owner; duplicated-support suggestions above identify small concrete targets rather than a demand for one giant harness.
